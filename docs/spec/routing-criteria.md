# Routing criteria — the package's default set

This document settles the vocabulary and the `suitableFor` / `avoidFor` assignments for the 12 archetypes shipped in the plugin. For these standard seats, the package owns the definitions, the tokens and the explanations; the user only picks `provider`, `model`, `modeId`, `thinkingOptionId` from the live catalog and then enables the seats they want to use. Tokens are displayed but cannot be edited on the form. The user can still create custom seats with free suitability; the boundary between the two seat kinds and the cost of that choice are in §7.

This is a contract for implementation, not a claim that the current code already does everything below. This editing pass only updates this document. The word "default" below means a package decision, effective without waiting for the user to fill anything in; the least certain decisions and the evidence that could change them are in §10.

## 1. What the package decides

| Decision | Why |
|---|---|
| Ship a closed vocabulary with the same definitions for every user, Lead and Jev. | The two fields are only comparable when they talk about one task space; do not let each pool invent its own meaning for a tag. |
| Ship both token lists ready-made for all 12 archetypes in §6. | The user is choosing a runtime to carry out work that has already been described, not composing that work. |
| Display a standard seat's tokens as read-only; custom seats are freely editable. | The package guarantees the meaning of the standard set; to diverge, create a custom seat rather than silently overwriting the shared contract. |
| Do not require every seat to declare every axis; allow token overlap between seats. | An axis that does not help discriminate need not be filled, and having the same suitability scope is a valid outcome. |
| Declaring all the domains a task requires takes priority over silence on domain, before cost is compared. | Matching work/depth does not prove the expertise obligation is met; tokens unrelated to the task create no advantage. |
| `avoidFor` is a suitability warning, not a prohibition. | Permissions, phases and review gates have their own contracts; the token must not masquerade as an enforcement mechanism. |
| A homogeneous pool still picks the cheapest/lightest adequate seat; it does not decline on a tie. | `no-suitable-option` is for the case where no suitable option exists, its current meaning at `plugin/server/runtime/cli/jev-routing.ts:91`. |
| The package maintains English guidance for Jev versioned together with the vocabulary. | English tokens alone are not enough to convey the meaning of AND/OR or `bounded`; the header currently marks Jev as English-primary and does not send `notes` (`plugin/server/runtime/cli/jev-routing.ts:10`). |

The reading baseline is the working tree of branch `feat/jev-routing`, HEAD `ef19372`, with uncommitted changes. The notation `archetypes.ts:line` below always points at `plugin/shared/archetypes.ts`. That file currently provides 12 templates, with empty provider/model and disabled (`plugin/shared/archetypes.ts:26`, `plugin/shared/archetypes.ts:38`). A comment still allows the Human to shape the list themselves (`plugin/shared/archetypes.ts:10`); the new contract moves responsibility for the meaning of the 12 standard templates to the package.

## 2. The four axes shared by both fields

| Axis | Question about the task | Closed value set, fully listed | Reason for keeping the axis |
|---|---|---|---|
| `work` | Which primary output makes the current assignment complete? | `enumerate`, `investigate`, `design`, `change`, `verify` | Distinguishes collecting, understanding, deciding, producing a change and verifying, even when they use the same tools. |
| `depth` | Before starting, which kinds of indeterminacy remain that must be resolved? | `mechanical`, `bounded`, `open` | Distinguishes an already-determined rule from a local decision and a still-open question; difficulty is not inferred from size. |
| `domain` | Which domain does the primary expertise obligation belong to? | `software`, `tests`, `prose`, `data`, `security`, `evidence` | Covers the specializations already present in the archetypes and Proof Auditor without turning a worker's name into a token. |
| `flow` | Is there a mandatory intermediate checkpoint that decides the next step? | `direct`, `staged` | Recognizes the need for coordination across phases with a signal readable before the run. |

The syntax of the **16 standard tokens** is `axis:value`, lowercase English, exact-match. The standard set has no synonyms, wildcards, self-made tokens or implicit inclusion relations. For example, `depth:bounded` does not automatically include `depth:mechanical`. This closed set constrains the content the package ships; it does not forbid free strings in a user's custom seats — how to read a pool containing both kinds is settled in §7.3.

| Situation needing classification | Package default | Why |
|---|---|---|
| One assignment both investigates and fixes. | Classify by the phase currently permitted: if the cause is not yet known, `investigate`; once the mechanism and fix direction are clear enough, switch to `change` before the fix phase starts. | The end goal does not erase the conditions of the current work; the Peer policy also splits authority by phase (`src/roles/peer.md:8`). |
| There are multiple independent outputs of equal rank. | Lead splits them into assignments/phases with clear primary outputs; do not attach multiple `work` values to the same task. | One route should not hide having to both decide a contract and independently verify that very contract. |
| One task has multiple domains. | Assign every domain carrying an independent acceptance obligation; using an extra tool or producing a secondary artifact is not enough to add a domain. | "Writing code to run tests" is not automatically two deliverables requiring acceptance. |
| The task lies outside the six domains. | Keep the concrete description in the brief; do not invent a token or force it into a wrong domain; keep routing by the knowable axes and the actual requirements. | The vocabulary serves comparison; it is not a permission list for performing tasks. The package only adds a domain when a recurring workload needs distinguishing. |
| The brief does not state domain tokens. | Infer domains from the actual obligations: checking auth bypass is still security, designing/running QC cases is still tests even when the brief never writes those token strings. | A missing label does not mean a missing obligation, so the expertise-priority step must not be skipped. |
| The brief lacks the facts needed to classify. | Lead supplements from the assignment and available sources; if a routing-deciding requirement is still missing, report that missing requirement rather than self-picking an easy label or treating domain as empty. | Missing information about the work is different from missing pool configuration; the user should not have to fix the taxonomy to remedy a poor brief. |

A task has at most one `work` value, one `depth`, one `flow`; `domain` may have multiple values under the rule above. This is a way of reading a brief, not a requirement for the user to enter four extra fields per assignment.

## 3. Definition of each value

### 3.1. `work` — the primary output

| Token | Sign observable before doing the work | Example | Confusable counter-example and why | Settled boundary and reason |
|---|---|---|---|---|
| `work:enumerate` | The output is an inventory, extraction or summary of a designated source; not a conclusion about cause, a design choice or an independent verdict. | List the places that read `avoidFor` and record the paths. | "List the usage sites then determine why routing is wrong" requires a causal conclusion — that is `investigate`. | Triage by an existing state or rubric is enumerate; finding a cause or basis not yet known is investigate, because "triage" itself does not say what the output must be. |
| `work:investigate` | There is a question with no known answer about cause, feasibility or technology choice; the primary output is an evidence-backed conclusion, possibly needing a throwaway prototype. | Find the cause of a flaky test, returning the mechanism and reproduction evidence. | Fixing a flaky test once the cause and fix direction are settled is `change`. | An investigation phase ends when the conclusion suffices to determine the next step with supporting evidence; the fix is a change phase, because finding the answer must be separated from applying it. |
| `work:design` | The output must propose or settle behavior, a contract, ownership or a structure not yet decided. | Propose ownership and lifecycle for a new routing module. | Writing test cases from settled requirements is not by itself design; it is `change` or `verify` depending on the primary output. | Choosing how to organize functions under a settled contract is still change; use design only when the contract/behavior decision itself is the deliverable. |
| `work:change` | Success requires handing over an altered artifact or state to be kept: code, tests, documentation or data; self-verification is part of proving the change. | Apply an approved codemod then hand over the diff and test results. | A prototype whose only purpose is answering "does the API meet the requirement?" is `investigate`; the code is not a deliverable to keep. | If a task has both research and a lasting deliverable, classify by the current phase; do not use the existence of a new file to decide work. |
| `work:verify` | There is a designated candidate, proposal, claim or evidence chain; the primary output is an independent verdict/findings against criteria. | QC: design and run test cases on a frozen candidate. | An engineer running unit tests for the patch they are writing is still `change`; self-proof is not independent verification. | A second opinion on an existing proposal is verify even before code exists; building a still-incomplete proposal yourself is design, because the object to be verified must exist. |

The engineering/self-proof, review and scouting boundaries have their basis in `src/roles/peer.md:25`; the menu also distinguishes design-before-code, write-own-scope, falsify and audit evidence (`src/roles/peer.md, bounded disposition outputs`). The tokens above name the task; they do not map disposition to model.

### 3.2. `depth` — how determined the problem is

| Token | Sign observable before doing the work | Example | Confusable counter-example and why | Settled boundary and reason |
|---|---|---|---|---|
| `depth:mechanical` | The brief has a transformation rule/checklist plus exception handling known well enough to decide the cases in scope; no new logic, cause explanation or exception design is needed. | Rename symbols by a defined mapping within an approved scope. | Also a rename, but requiring decisions on API compatibility and alias behavior: the mapping does not yet determine the answer, so it is no longer mechanical. | Only count a rule as sufficient when the exceptions seen also have determined handling, because "most files are alike" does not guarantee the rest needs no judgment. |
| `depth:bounded` | The goal, acceptance and related contracts are stable; implementation choices or ways of checking remain within those boundaries, with no major unknown handed over to be resolved. | Add validation per a settled spec and error format, choosing the function organization and tests yourself. | "Only fix one file" but the cause of the race condition is unknown: small size does not make a problem bounded. | A choice that only varies how an existing contract is implemented is bounded if not already mechanical, because no file-count or line-count threshold is needed. |
| `depth:open` | The task must resolve unknowns that can change acceptance, correct behavior, the causal mechanism, feasibility, compatibility or ownership; it needs hypotheses built/refuted or options weighed. | Find the mechanism behind lost updates when multiple writers run concurrently, and distinguish the hypotheses. | A codemod over thousands of files under a complete rule is still mechanical; large volume does not by itself create openness. | One of those unknowns suffices to assign open when it is a question the task must answer; reading documentation to find an existing function name is not by itself open, because looking up a fact differs from resolving an unknown in the problem. |

**Fixed detection order: `open` → `mechanical` → `bounded`.** Check for major unknowns first; if none, check whether a fully deciding rule exists; if it is not mechanical but acceptance/contracts are stable, it is bounded. A poor brief must not default to bounded: Lead must gather the missing facts per §2.

**`depth` is not a capability scale or a "model smartness" level.** It describes the task's nature; it does not rank provider, model or reasoning setting. A seat suitable for open is not automatically declared suitable for every mechanical task. A mechanical task can take a long time or impact hard-to-reverse data; risk and volume must still be described in the brief.

The decision not to use line-count, file-count, hour or model-name thresholds: those quantities do not determine the kind of indeterminacy. The current source tags already distinguish bounded-fix, open-design/deep-debugging and mechanical-change (`archetypes.ts:43`, `archetypes.ts:47`, `archetypes.ts:75`).

### 3.3. `domain` — the domain of the primary obligation

| Token | Sign observable before doing the work | Example | Confusable counter-example and why | Settled boundary and reason |
|---|---|---|---|---|
| `domain:software` | Acceptance requires judging or changing software behavior, an API, a module, a lifecycle or a runtime error. | Investigate a binding-resolution failure or implement an API per spec. | Fixing a typo in a README produces prose; it does not by itself need software. | Documentation only adds software when it must establish/verify technical behavior, because naming an API does not create an independent technical obligation. |
| `domain:tests` | A test-case set, test harness, requirement coverage or a test campaign is the primary obligation handed over. | Generate a test set from a spec then check a candidate with those cases. | An engineer adding unit tests to prove a feature is still primarily software; not automatically an independent test-authoring task. | Assign tests when the test set or test results are separately accepted; only add software when there is a separate obligation about implementation or contract beyond the test product, because writing tests in code does not create a second obligation. |
| `domain:prose` | The quality, meaning or accuracy of documentation/translation is the product or primary object of acceptance. | Rewrite an installation guide or translate a document whose content is settled. | A report on a regression's cause uses prose but its acceptance lies in the failure mechanism; not by itself prose. | A spec recording existing decisions is change/prose; a spec that must decide software behavior is design/software, plus prose if the document also has its own acceptance requirements. |
| `domain:data` | Acceptance checks record invariants, persisted schema, mappings, backfill or the target data format. | A backfill with checks on counts, mappings and recoverability. | Renaming a type in source without changing persisted schema or data is software. | A not-yet-run script still belongs to data if the accepted product is a persisted schema/data transformation; whether it has run does not decide the domain. |
| `domain:security` | The brief requires judgment about a threat model, abuse cases, trust boundaries, auth, secrets or dependency risk from an adversarial viewpoint. | Check auth bypass against a threat model. | Adding a display field to the response of an authenticated endpoint is not by itself security if it neither changes nor checks a security boundary. | Always add security when a task changes/checks a trust boundary, access rights or secret handling; merely using an authenticated component is not enough, to avoid turning every feature into a security task. |
| `domain:evidence` | The primary evaluation target is an evidence chain: did the command run, does the output prove the claim, is the candidate identity correct. | Cross-check a test log against the snapshot a report claims to have checked. | Reading a log to find an error's cause is still software; the output is not a verdict about the report's trustworthiness. | Assign evidence when the provenance, identity or probative strength of a claim must be checked; not merely because the task reads logs, since logs are a tool of many kinds of work. |

The domains create no implicit hierarchy: security is not an alias of software, tests is not an alias of verify. Only assign multiple domains when there are multiple separate obligations. The six values are this version's closed set because corresponding outputs already exist in the archetypes or the menu; the package does not add a vague `other` to appear to cover every task (`archetypes.ts:59`, `archetypes.ts:63`, `archetypes.ts:67`, `archetypes.ts:83`; `src/roles/peer.md, bounded disposition outputs`).

### 3.4. `flow` — checkpoint structure

| Token | Sign observable before doing the work | Example | Confusable counter-example and why | Settled boundary and reason |
|---|---|---|---|---|
| `flow:direct` | The assignment and protocol allow completing the scope then handing back once, with no mandatory intermediate checkpoint conditioning the next phase. | Look up inventory then return a report in the session. | A migration that must verify a trial batch before running in full is staged even if each batch is very fast. | Direct can contain many commands or run long; an ordinary check before handback creates no new stage, because the number of operations says nothing about the permission/dependency structure. |
| `flow:staged` | There are mandatory phases/checkpoints; evidence or decisions there determine whether to continue, change scope, or require wait/resume. | A backfill in waves, confirming invariants and recovery conditions before the next wave. | A single analysis that takes hours then returns results is not by itself staged; duration does not prove a checkpoint exists. | Only count a checkpoint that lies inside the assignment/protocol or is an actual condition of the next step; do not add one just to match a seat's name. |

By default, read the workflow from the assignment and the protocol in force: with a sufficient-condition checkpoint it is staged, without one it is direct. If the necessary protocol cannot yet be read, this axis is undetermined — that is Lead's context-gathering job, not a configuration box the user must fill. The reason for this boundary is that a checkpoint is observable before doing the work, fitting the current phase/prerequisite rule (`src/roles/peer.md:8`), while run duration also depends on the runtime.

## 4. Combination, absence and seat-selection rules

| Settled rule | How to read it and why |
|---|---|
| `suitableFor`: OR among values of the same axis, AND across the declared axes. | `work:change`, `depth:mechanical`, `depth:bounded` means change with depth mechanical or bounded; this checks existing assertions — it is not yet a conclusion that the seat meets every obligation not yet declared. |
| A task with multiple domains must be supported on each domain. | A seat declaring software and tests can support either domain or a task needing both; declaring only tests must not let the product-fixing obligation of a task needing both be dropped. OR over the value set is a choice per obligation, not a license to drop an obligation. |
| Declaring all required domains takes priority over declaring them partially or not at all. | When the other requirements are all suitable and warnings have been handled, a seat declaring all of the task's domains goes into the priority group; a seat declaring only part or omitting the domain axis goes into the fallback group. The rule applies equally to all six domains; no privileged domain group is created. |
| `avoidFor`: OR over the whole list. | `depth:open`, `domain:data` warns on open or data; not only on a task that is both open and data. One intersecting domain already creates a warning. |
| Avoid beats suitable advice when both match. | The conclusion is "has suitable points but the warning must be handled"; do not sum scores to erase a warning and do not auto-drop the seat. Lead/Jev may still pick it if the task's specific reason shows it is adequate. |
| One token in both fields is a contradictory assertion. | On a standard seat this is a package content error to fix in the next package version; on a custom seat show a warning but do not fix the user's content for them. When reading, avoid still beats suitable advice. The §6 token set has no such conflict. |
| An absent axis means **no suitability assertion on that axis**. | It is still "no information yet", not "supports every value"; omitting domain keeps the seat considerable but does not put it level with a seat that declares the full domains. Omitting an axis is a complete package choice, not a blank awaiting the user. |
| `avoidFor: []` means the package sets no general warning for that seat. | This is a settled value, not a remainder awaiting input nor a promise of "can do everything". `suitableFor: []` says there is no positive description and is not used for any standard seat in §6. |
| No scoring by token count or number of declared axes. | Only whether **the domains the task demands** are fully declared matters; adding unrelated domains, repeating tokens or declaring more axes does not raise priority. Two seats both declaring all required domains are equal on this criterion even if one has more tokens. |
| Token overlap between seats is valid. | The package keeps the duplication when the task scope is the same; only the user-chosen runtime can create a cost or quality difference. |
| Missing facts are not by themselves infeasibility. | A poor brief must be clarified; an empty axis, an avoid warning or tied options are not reasons to return `no-suitable-option`. |

**Fixed selection order:**

1. Determine the task's obligations from the brief and assignment sources: work, depth, flow and the set of domains actually needed. "Review patch" with no content does not yet permit concluding the task has no domain obligation. When the brief has enough content, do not make the user write domain labels themselves.
2. Consider the options eligible by runtime, the assignment's independence/permission requirements, and work/depth/flow suitability; an avoid warning must be explained if the seat is still chosen. Declaring one domain correctly does not erase a wrong work, a warning or an unmet runtime constraint.
3. Among the still-suitable seats, prioritize the group **declaring all of the task's domains**. If at least one adequate seat exists in this group, do not pick a domain-missing seat just because it is cheaper. Price must not be used to turn a still-missing assertion into an existing one.
4. Only consider the fallback group when the fully declaring group has no seat meeting the task. To choose a fallback seat, Lead/Jev must have a concrete basis for each undeclared obligation from supplied facts — for example comparable results tied to the binding, or suitable capability information provided by the package/provider; the name "deep", missing warnings or a low price are not enough. The basis must be present in the brief/state Jev actually receives, not only in local notes. Do not make the user build a corpus or fix tokens to use this mechanism.
5. **Within the group currently being considered and already adequate**, choose the lowest expected execution cost from trustworthy metadata; if price is missing, prefer the lighter thinking when provider/model are equal and the provider has a clear thinking order; if still tied, choose ascending `option.id`. Do not decline on a tie, and do not claim an ID tie-break has proven the cheapest seat. Do not ask the user to fill in price, priority or a model ranking table.

If no seat declares the full domains and there is also no basis for a fallback seat, the decision-preparation step must report **missing basis regarding domain** and supplement the facts before releasing an automatic choice. This is not `no-suitable-option`: unknown does not mean infeasible. When every seat is genuinely adequate and in the same group — including a homogeneous pool — step 5 still applies. The missing-facts reporting mechanism is a plan requirement, not an outcome already present in the current Jev API.

**Why this rule was chosen:** the package prefers an assertion directly relevant to the task's obligations over silence; it does not score list length, does not certify model capability and does not turn suitability into a permission filter. A multi-element domain set is still checked in full: a seat declaring two of three domains does not automatically beat a seat declaring one of three by score; both are fallback for the missing obligations.

| Mandatory reading case | Decision under the new rule |
|---|---|
| Verify/security; security-review and independent-second-opinion are both usable on the other requirements, no warning currently matches. | Security-review is preferred because it declares security; independent-second-opinion's lower price is not enough to reverse the choice. |
| Verify/tests on a frozen candidate; test-authoring and independent-second-opinion are both usable on the other requirements. | Test-authoring is preferred because it declares tests; "verify" alone does not claim test expertise. |
| Verify/tests/security; one seat declares only tests, another declares only security. | Neither seat declares fully; do not choose by token count or price before there is a basis for the missing part — or split the obligations if the assignment allows. |
| Two seats both declare security; one also declares tests but the task only needs security. | The two seats are equal on domain coverage; the extra tests token does not help win, so cost decides once both are adequate. |
| The brief requires checking auth bypass but does not state `domain:security`. | Still recognize security from the content and apply domain priority; do not drop to tie-breaking over a missing label. |
| The brief only says "review patch", with no patch or criteria to determine the obligations. | Supplement the task content; do not treat every generalist as adequate, and do not decline for lack of context. |

The reason for the **price** fallback: the package must be able to choose among already-adequate seats even when cost metadata is missing; this fallback does not apply to filling a gap in expertise obligations. The current payload only has id/provider/model/suitability, not thinking or price (`plugin/server/runtime/cli/jev-routing.ts:83`); implementing the full data is the package's responsibility, not pushed onto the user as more tags. The current `no-suitable-option` already carries the meaning that no option is suitable (`plugin/server/runtime/cli/routing.ts:96`).

**Settled expressiveness limits:** flat suitable describes a product of per-axis value sets; it cannot express exactly "software mechanical or prose open" without also accepting the two cross combinations. Flat avoid cannot express an AND condition across two axes. This version adds no clause syntax: keep the archetypes simple and use the brief to explain exceptions, because the 12 templates do not yet need their own expression language. §6.1 records the intended meaning changes versus the old tags.

## 5. Task and runtime permission are two different things

| Content | Package decision |
|---|---|
| A `mode` axis / a `mode:read-only` token. | Not in the vocabulary. Do not use the same label for "the task needs no writes" and "the runtime cannot write". |
| The task only needs to read or return a report. | Record the intended impact and write scope in the assignment; `work:enumerate` by itself does not forbid writing a permitted report. |
| The runtime cannot modify the candidate. | Check the effective permissions of host/sandbox/tools; do not use disposition, model name or avoidFor as certification. |
| A checker needs to write tests/reports. | Possible within its own granted scope while still being work verify; do not conflate verify with forbidding every write. |
| Independence from the writer. | Cross-check session/binding and the assignment's review-gate requirement; the seat name independent-second-opinion does not by itself guarantee that. |

The current Peer policy separates disposition from write permission and allows explicitly assigned artifact writes (`src/roles/peer.md:1`, `src/roles/peer.md:36`). Cross-family review is also a relationship with the writer, not a permanent property of a provider (`src/references/review-gates.md:26`). `optionExclusions` currently only considers enabled/availability/role (`plugin/server/runtime/cli/routing.ts:86`); this document does not change it into a suitability enforcement mechanism.

| `data-migration` | `["work:change", "domain:data", "flow:direct", "flow:staged"]` | `[]` | The seat produces data or persisted-schema transformations, including both one-step conversions and multi-checkpoint backfills, so no general warning applies to every accompanying piece of software work. |

### 6.1. Intended meaning changes versus the old tags

| Seat | The package's settled new reading | Why the old strings are not kept |
|---|---|---|
| `lightweight-recon` | Triage lives on this seat only when classifying/summarizing by known criteria; "read-only" continues to live in the assignment. | A triage tag can hide an investigation, and writes are an impact/permission, not a single work type (`archetypes.ts:39`). |
| `standard-coding`, `test-authoring` | Both can write tests independently; test-authoring is additionally described for verdicts on a frozen candidate. | Chose to keep both the test-writing/spec-to-testcases meaning and the QC meaning in the notes, rather than forcing one of the two to disappear (`archetypes.ts:43`, `archetypes.ts:59`). |
| `deep-reasoning` | Warns on every mechanical task, including checklist checking. | The package chooses thrift for all rule-following work, broader than the old routine-inventory/mechanical-change; this is a warning, not a ban on choosing the seat (`archetypes.ts:47`). |
| `autonomous-long-running` | Its default specialty is staged; a long-running but single-pass job is not preferred merely for being long. | The long-running/multi-step tag does not say whether a checkpoint exists, so the package chose the observable sign; avoiding direct is broader than the old quick-lookup and is recorded as a less-certain decision in §10 (`archetypes.ts:55`). |
| `spec-docs-writing` | Spec-writing on this seat is expressing existing decisions; deciding new behavior follows work design. | "Spec" can be a document or the design decision itself; separating the two outputs avoids routing a technical decision as prose writing (`archetypes.ts:63`). |
| `test-authoring`, `spec-docs-writing` | Domain software is a warning when the task has an independent obligation about the product; using code to write tests or naming an API in docs is not enough to trigger it. | This generalizes implementation/architecture/debugging without banning every artifact bearing technical content (`archetypes.ts:59`, `archetypes.ts:63`). |
| `security-review` | Accepts both design/security and verify/security; warns on every change. | A threat model can be created before code exists, while fixing the product needs separate ownership; the change scope is broader than the old feature-implementation/mechanical-change (`archetypes.ts:67`). |
| `debugging-root-cause`, `research-spike` | The investigation phase ends before the product-change handover phase; both seats warn on work change. | This decision is broader than avoiding greenfield or production-only: every lasting deliverable must be evaluated as a change assignment (`archetypes.ts:71`, `archetypes.ts:79`). |
| `mechanical-refactor` | An exception needing a handling choice takes the task out of mechanical scope. | "API migration" belongs to this seat only when the rule already determines the behavior; the name migration does not guarantee it is a codemod (`archetypes.ts:75`). |
| `research-spike` | A purely enumerative API survey goes to lightweight-recon; the spike seat focuses on open questions. | Keep the feasibility/technology-comparison focus instead of using one seat name for both lookup and research (`archetypes.ts:79`). |
| `data-migration` | Accepts both direct and staged; does not translate interactive-feature-work into a blanket software warning. | Format conversion does not always have multiple phases, and a flat list cannot express "interactive feature" specifically without falsely warning other work (`archetypes.ts:83`). |

### 6.2. Duplicate and overlapping cases

- `debugging-root-cause` and `research-spike` keep **the same entire suitable**: investigate, open, software. Do not create a new token to force them apart; whether the question is causal or feasibility still appears in the brief.
- `standard-coding` and `mechanical-refactor` can both accept change/mechanical/software. Throughput in a seat's name/description does not prove the user-chosen binding is cheaper; apply the adequate-seat selection rule in §4.
- `standard-coding` and `test-authoring` can both accept change/bounded/tests. Work verify helps distinguish the independent-verification purpose; it grants no extra permission and creates no review gate by itself.
- `deep-reasoning`, `independent-second-opinion` and `security-review` can all match work verify; that does not yet put them level on domain. For verify/security, security-review is in the fully declaring group while the two seats declaring no domain are fallback per §4.

**The intent of deep-reasoning:** keep a general reasoning seat to weigh across many domains without claiming it is specialized enough for every domain. AND across the declared axes only confirms its work/depth is not contradictory; omitting domain creates no capability wildcard. The previous version letting it drop straight into price comparison with specialists is the very logic error just fixed. Do not add a batch of domains to this seat to paper over the gap; it needs a basis for the specific obligation when chosen as fallback.

## 7. What the user fills in

### 7.1. Package-provided standard seats

For **each standard seat the user wants to enable**, the user only makes the following choices:

| Field | The user chooses | Default and why |
|---|---|---|
| `provider` | An available provider from live discovery. | A seat with no provider chosen stays off; do not guess a provider for the user because this is their account/runtime. |
| `model` | A model published by the chosen provider in the live catalog. | Do not fill a sample ID or inherit the Lead's model; the model must belong to the actually chosen provider. |
| `modeId` | A mode published by the chosen provider in the live catalog, or the "Provider default" choice. | Defaults to Provider default; a stored mode the catalog no longer lists stays visible under the "(stored)" escape — do not auto-materialize an unknown default into an ID. |
| `thinkingOptionId` | A thinking option the model publishes, or the "Provider default" choice. | Defaults to Provider default; if the model declares no thinking option, **no thinking control is rendered at all** and no fake ID is sent, because not every provider separates thinking from the model (host parity: the host's thinking control exists only when `selectedModel.thinkingOptions.length > 0`). |
| Enable/disable | Enable the seat once it has a valid runtime; disable the seats you do not want to use. | Do not require configuring all 12 seats before the pool can be used. |

A standard seat's `suitableFor` / `avoidFor` **appear but cannot be edited on the form**, with a "Package-managed" indicator and a "Định nghĩa token" (Token definitions) button opening a lookup section right inside the card (§7.4.F). The standard ID is also read-only so that a rename cannot silently turn a standard seat into a custom one. The user does not need to author roles, notes, axis definitions or tie-break rules; those defaults are package-provided. The user is also not asked to fill a cost table or label a historical task set.

The reason for locking tokens: the 16 tokens carry shared meanings that the package has defined, illustrated and explained to Jev; allowing local overwrite would change a standard seat's meaning while the reader still believes they are using the standard version. This is a contract about the form's contents and how a seat is identified — not a filesystem write-block mechanism or a model certification.

Mode is a user pick on both seat kinds — the same catalog picker and free-text fallback as Custom — while feature values keep the configured provider/host defaults and display as a package-owned read-only summary on standard seats. Neither mode nor features self-raise permissions from suitability or add a permission-picking step to the seat setup flow. Initial availability and the peer role are filled by the package. The templates already set `roles: ["peer"]`, disabled and availability ready (`archetypes.ts:26`); the thinking picker already has Provider default and renders nothing at all when the model declares no options (`plugin/client/cards/peer-pool.tsx:1238`). The routing-prose and feature locks on standard seats follow §7.4.B — mode is not part of that lock.

User-chosen models may still lack the capability for the work; the package describes the work consistently — it does not certify every model as equivalent. When outcomes are poor, swapping the runtime or disabling the seat is the standard-seat configuration remedy.

### 7.2. Custom seats and identification by ID

**Choose exact ID-matching; add no provenance field to the catalog.** The ID set in `PEER_SEAT_ARCHETYPES` is the name set reserved for standard seats; every other ID is a custom seat. Do not use a prefix, suffix or token similarity to guess provenance. So `security-review` is a standard name, while `my-security-review` and `security-review-2` are custom names.

This convention determines the **current management mode**; it does not prove who created a seat. A historical user may have legitimately set a standard ID; the code currently only bans duplicate IDs within the same catalog — it does not yet reserve package names (`plugin/server/runtime/cli/routing.ts:19`). Conflicts must be handled transparently per the following table, rather than claiming an ID proves provenance.

| Situation | Settled behavior |
|---|---|
| Create a standard seat from the picker. | Use the exact canonical ID; if that ID already exists, open the existing seat or report a conflict — do not auto-generate a suffixed standard copy. |
| Want to adjust tokens or have another binding from the same template. | Use the explicit action "Tạo ghế riêng từ mẫu" (Create a custom seat from template); copy the values into a new non-reserved ID, label it Custom and let the fields be edited. This is a deliberate custom-seat creation, not a standard seat spontaneously losing its lock. |
| Create/rename a custom seat to a standard ID, even when the standard seat is not yet in the pool. | The form refuses the reserved name and suggests an unused custom ID; the user may still set every other valid ID. Whether the name is reserved does not depend on whether the standard seat is currently present. |
| A custom seat uses a non-reserved ID but copies the exact standard tokens. | It is still Custom and still editable; identical contents do not make it package-managed. |
| Load/import hits a standard ID and a token set matching the package version in use. | Display it as a standard seat — its package-owned fields (ID, tokens, feature values) read-only while provider/model/mode/thinking — and local-only notes — stay user-picked; if the former owner wants to keep managing it themselves, use the create/convert-to-custom action rather than editing the ID directly on a standard row. |
| Load/import/upgrade hits a standard ID but tokens differ from the package version. | Display "Token conflict" with both the stored and the standard contents; no overwriting, no pretending they are in sync, and do not continue storing that seat as a valid standard seat. The user chooses to use the standard set or converts the existing seat to a custom ID to keep its contents. |
| Choose to use the standard set during a conflict. | Preview the token change before Save; keep the current binding and enabled state — do not auto-change the model or permissions. |
| Choose to convert a conflicted seat to custom. | Keep the current tokens and configuration, move to a custom ID and update in-pool references such as quotaFallback in the same action; clearly report that references outside the pool must be re-read/updated — do not auto-fix elsewhere. |
| The package has a new token version. | Standard seats on old tokens go through the same conflict/update flow — no silent update on Load; custom seats receive no automatic token updates. When exporting JSON, export exactly the chosen state rather than sneakily substituting the new standard version. |

Compare the standard token set by exact value set, not entry order; added/removed/changed-value tokens create a conflict. The token update must not silently change a running pool. A conflict is a content error with its own fix path — not `no-suitable-option`; the routing read/prepare path must report the conflict before using that seat as a standard seat. Unrelated seats keep their data untouched.

To keep ID-matching meaningful across package versions, do not reuse a standard ID for different work and do not remove an ID from the registry without a path to convert old pools. Similarly, do not change the meaning of a released token under the same string: if a different meaning is needed, create a new value in the next vocabulary version. Comparing only IDs and tokens cannot detect a semantic change that leaves no difference in the data; that is the package's compatibility responsibility, not a reason to add provenance for the user.

**Two required changes to the current form:** `addSeat` currently auto-uses `uniqueSeatId` to generate a suffix (`plugin/client/ManagerSurface.tsx:973`; `plugin/client/manager-state.ts:619`), and the ID is directly editable, with quotaFallback remap (`plugin/client/ManagerSurface.tsx:930`, `plugin/client/ManagerSurface.tsx:1880`). The new flow separates "add a standard template" from "create a custom seat", locks standard IDs and keeps reference updating when the user deliberately converts to a custom seat.

No schema extension is needed: zod and `validateCatalog` keep checking data shape the same way; reserved-name and standard-content checking is a separate semantic check shared across the related form/save/routing-read paths. Do not just disable the input in the client while still saving a standard seat with different tokens. The parity test already compares each verdict between the two validators (`tests/plugin-routing.test.mjs:557`); do not make the general validator reject a custom seat's free strings just to lock standard seats.

### 7.3. Freedom and cost of custom seats

A custom seat may freely edit a non-reserved ID, suitability, notes and other configuration within valid data/runtime shapes. **A custom seat's tokens are not required to be among the 16 standard values** — no auto-translation, deletion or forcing into an archetype. The user may write prose or their own vocabulary; English is recommended since Jev is English-primary — not made into a new schema prohibition.

The default escape path is creating a custom seat from a template then editing, possibly disabling the standard seat if both are not wanted. The real cost is an extra ID and configuration to manage, possibly having to update places that reference the seat, and no longer auto-receiving the package's token fixes. The package does not guarantee custom prose/tags are understood as consistently as the standard vocabulary; the user is responsible for the content they customize. Opening the customization path does not make standard seats editable.

In a pool with both kinds, an **exact verbatim standard token** on a custom seat is still read by the shared definition and joins the §4 domain test; a package seat is not preferred merely for the ownership label. A custom string like `security-expert` is not automatically counted equal to `domain:security`, and custom prose does not change how the package/Jev interprets the 16 standard tokens. Jev may still consider custom content as suitability context, but any part lacking a standard domain assertion must go through the fallback check in §4. That is the trade-off of customization — not a ban on creating or storing custom seats.

### 7.5. Repository catalog and user-scope pool: precedence and drift
